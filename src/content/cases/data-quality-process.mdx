  <section id="approach">
    <p class="eyebrow">{'02 / Framework and operating approach'}</p>
    <h2>{'Reuse the checking pattern while keeping rules specific to each dataset'}</h2>
    <p>
      {
        'I built a reusable framework with table-specific implementations. Common database, checking, reporting, and export patterns could be reused, while each dataset retained the rule configuration needed for its own structure and business meaning.'
      }
    </p>
    <p>
      {
        'The framework used read-oriented PostgreSQL access and automatic audit-period handling. It produced local audit outputs rather than writing changes back to the database.'
      }
    </p>

    <h3>{'Translate definitions into repeatable checks'}</h3>
    <p>
      {
        'The table-specific configurations applied reusable checks for completeness, uniqueness, validity, ranges, categories, patterns, dates, nullable fields, and text cleanliness. Explicit missing-column and exceptional-condition handling kept structural failures visible instead of silently dropping a check.'
      }
    </p>
    <p>
      {
        'Each check produced a rule-level PASS or FAIL status with supporting counts, rates, and affected-record detail. A passing rule meant that its configured condition was met for that audit; it did not guarantee that the complete dataset was perfectly correct.'
      }
    </p>

    <h3>{'Give each audience evidence it can use'}</h3>
    <div class="output-groups">
      <div>
        <h4>{'Management and analyst monitoring'}</h4>
        <ul>
          <li>{'Data-health summaries and health classifications'}</li>
          <li>{'Column scorecards, charts, and visual rule matrices'}</li>
          <li>{'A consistent view of where attention was concentrated'}</li>
        </ul>
      </div>
      <div>
        <h4>{'Technical and data-owner follow-up'}</h4>
        <ul>
          <li>{'Rule-level results and detailed exceptions'}</li>
          <li>{'Correction-ready extracts and owner-routed material'}</li>
          <li>{'Enough detail to investigate findings without changing the source'}</li>
        </ul>
      </div>
    </div>

    <h3>{'Make responsibility explicit'}</h3>
    <p>
      {
        'I authored the operating protocol and coordinated its implementation with Data Engineering. Data Engineering owned upstream ingestion and later took over recurring execution of the automation I created. Relevant technical and business owners controlled field definitions, and source owners retained responsibility for correction.'
      }
    </p>
    <p>
      {
        'The handoff transferred recurring execution, not authorship of the framework. My contribution remained its analytical design, implementation, reporting structure, cycle comparison, and operating-process development.'
      }
    </p>

  </section>

<section id="validation">
  <p class="eyebrow">{'04 / Validation, comparison, and correction boundaries'}</p>
  <h2>{'Compare cycles and keep open findings visible'}</h2>
  <p>
    {
      'I compared recurring audit cycles so reviewers could distinguish corrected findings from unresolved issues and newly detected regressions. Open findings remained visible instead of disappearing when a new report was generated.'
    }
  </p>
  <p>
    {
      'I classified and packaged exceptions for the owners able to interpret or correct them. Ambiguous findings could be escalated for clarification, while the audit trail retained the rule result, exception detail, and follow-up status.'
    }
  </p>
  <p>
    {
      'The framework used read-oriented access and did not write corrections back to PostgreSQL. Detecting an exception did not prove that the source had been corrected; relevant source owners retained remediation responsibility.'
    }
  </p>
</section>
